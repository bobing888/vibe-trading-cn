## 三、关键教训（5 条铁律）

### 教训 1：多周期共振是常识，不是"高级选项"

**金融工程基本规则**：
- 大周期（1d/4h）定方向
- 中周期（1h/15m）找节奏
- 小周期（5m/1m）定入场
- **单周期 = 单视角盲人摸象**

**误判原因**：我以为 user 说的是"提高响应频率"，实际是"综合多周期分析"。
**正确理解**：user 期望"金融界标准做法"——多周期共振。

### 教训 2：写完文档 ≠ 完成（独立审查是必经步骤）

**违反 `verification.mdc` 铁律**："没有新鲜的验证证据，不许宣称完成"。
**违反 `code-review.mdc`**："早审查、勤审查、严分级、说人话"。
**违反 `systematic-debugging`**："根因不明不动手"。

**正确做法**（我现在才补上）：
1. 写完文档 → 派 `generalPurpose` subagent **独立只读审查**
2. 按 CRITICAL / IMPORTANT / MINOR 三档分类
3. **所有 CRITICAL 必须修复后才能宣称完成**
4. 重要修改后再跑一次审查（直到 0 CRITICAL）

### 教训 3：架构层面要先验证依赖假设

**v3.4 的 3 个致命假设（实现前必须验证）**：
- 基座是否真的支持 1d/4h/15m 周期（v3.3 只用 1m/5m）
- 基座 5 preset 名字是否真实存在
- 基座返回字段名（`trend` / `change_pct` / `atr`）是否齐全

**违反 `verification.mdc`**："拿数字说话，没数字闭嘴"。
**正确做法**：在任务 1 加入 **强制前置条件**——不通过不进入任务 2。

### 教训 4：响应速度分层（不能"一刀切 1 分钟"）

**违反 `chinese-style.mdc`**：含糊化"1 分钟响应"导致架构与目标矛盾。
**正确做法**：
| 响应类型 | 时间 | 是否跑 5 preset |
|---|---|---|
| **数据跟踪** | 每 60 秒 | ❌ 轻量 |
| **异常响应**（4h 反转 / 1m 插针 / 持仓亏）| **1 分钟内** | ❌ 不依赖 preset |
| **日常推荐** | **5-10 分钟内** | ✅ 跑 preset + 缓存 5 分钟 |

### 教训 5：设计承诺 vs 代码实现必须一一对照**

C4 教训**：WEAK 推 0.5% 仓位——**设计写了，代码没写**。
**正确做法**：
- 文档每条规则 → 实施计划对应一条测试
- **无测试覆盖的规则 → 等于不存在**
- 计划文档测试清单必须 100% 覆盖设计文档的所有规则
